Configurable chat attachment size limits

Agent Canvas · frontend (this repository) · supersedes the hard-coded 3 MiB attachment cap

The problem

src/utils/file-validation.ts hard-coded a 3 MiB ceiling on chat attachments — both per file and for a whole selection — and built its error messages from the literal "3MB". There was no configuration channel at all: no env var, no flag, no setting. The agent-server imposes no attachment-size cap of its own, so this frontend check was the only thing standing between a user and a larger upload. 

// before — src/utils/file-validation.ts
const MAX_FILE_SIZE  = 3 * 1024 * 1024;   // per file
const MAX_TOTAL_SIZE = 3 * 1024 * 1024;   // all files in one message

A deployment that needed a 40 MB PDF export or a log bundle had to patch the compiled bundle at image build time and carry that fork.

The constraint that shapes the fix

Not every attachment travels the same way. Images the user marks embed are base64-encoded into chat events and sent as WebSocket frames the SDK caps at 4 MiB (session_protocol.MAX_FRAME_BYTES). Base64 inflates by ~4/3, so a 3 MiB image becomes ~4.1 MiB and would be dropped in flight. Workspace file uploads go over HTTP and are unaffected by that ceiling.

So the answer is not "remove the limit" and not "raise one number". It is two configurable ceilings for the HTTP path, plus one fixed ceiling for the WebSocket path.

After

CeilingDefaultConfigurableWhy
Single attachment 200 MiB yes HTTP upload — no server cap to match
Combined selection 200 MiB yes HTTP upload — bounds one message
Embedded image 3 MiB no — fixed 4 MiB WebSocket frame cap × base64 inflation

Before

  • One 3 MiB number for both limits
  • Error text literally says 3MB
  • No way to change it
  • Embedded and uploaded files treated alike
  • Rebuild the image to change the value

After

  • Separate per-file and combined ceilings, both 200 MiB
  • Error text derives from the effective byte value
  • Env var, static-server flag, or runtime global
  • Embedded images keep their own 3 MiB ceiling
  • Env change + restart — no rebuild

Where the limit is resolved

New module src/utils/attachment-size-limit.ts owns the resolution. The precedence mirrors the one src/utils/base-path.ts already uses, and is source-major: build-time beats serve-time, and within each source the per-limit variable beats the shared one.

1Build time — VITE_MAX_ATTACHMENT_FILE_MB → VITE_MAX_ATTACHMENT_SIZE_MB
for deployments that build their own bundle
2Serve time — window.__AGENT_CANVAS_MAX_ATTACHMENT_FILE_MB__ → window.__AGENT_CANVAS_MAX_ATTACHMENT_SIZE_MB__
injected into index.html by scripts/static-server.mjs; the Docker image and the published binary can be retuned without a rebuild
3Default — 200 MiB per file and 200 MiB combined
a missing, non-numeric, or non-positive value falls back here, so a typo in a deployment's config cannot silently remove the limit

The embedded-image ceiling is not part of this chain. It is a constant in the same module, because it is bound to a transport property rather than a deployment choice.

Compatibility and risk

  • No API change. The agent-server contract is untouched; this is purely frontend configuration plumbing over the existing runtime-injection channel.
  • The default moves. A canvas built from this branch accepts larger attachments than one built from main. That is the point of the change, but it is a behaviour change worth a maintainer's explicit sign-off.
  • Backend-side cap unchanged. The agent-server still applies FILE_UPLOADS_MAX_FILE_SIZE_MB on its side; the frontend ceiling is an independent, user-facing check.
  • The SDK's HTTP timeout is a separate concern. The TypeScript client has a hard-coded 60 s upload timeout. A 200 MiB upload over a slow link can hit it. That lives in OpenHands/software-agent-sdk, not here.
